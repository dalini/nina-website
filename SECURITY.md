# SECURITY

`SECURITY.md` owns the security posture of nina-laaf.de: threat model, security requirements, controls and trust-boundary enforcement. Behavior: `REQUIREMENTS.md`. Components and boundaries: `ARCHITECTURE.md`. Browser-facing design: `DESIGN.md`.

## Required Security Inputs

- Requirements source: REQUIREMENTS.md
- Design source: DESIGN.md
- Architecture source: ARCHITECTURE.md
- System purpose: See REQUIREMENTS.md
- Application profile: See ARCHITECTURE.md (Architecture): static public site built by Hugo with no server-side code serving visitors, plus a self-hosted Sveltia CMS editing interface with its GitHub OAuth helper (the only server-side code reachable from the internet) and a GitHub Actions build/publish pipeline; everything served by nginx on one rented VPS in Germany, which also runs the content check, the Instagram token refresh and the Content Store backup. Visitor statistics come from Google Analytics in visitors' browsers on the public site (SEC-PRIV-5).
- Users / actors / roles: Visitor (anonymous, read-only); Editor (Nina and Ives); Owner (Nina and Ives, SEC-AUTHZ-2); Maintainer (Ives: admin of `dalini/nina-site` and `dalini/nina-content`, CI, VPS, registrar and DNS); build/deploy identity; Instagram (external).
- Public interfaces and trust boundaries: TB-1 visitor browser ↔ Static Hosting (nginx on the VPS, including the domain and DNS of `nina-laaf.de`); TB-2 editor browser ↔ Editing Interface (`edit.nina-laaf.de`) and preview site (`preview.nina-laaf.de`); TB-3 Editing Interface ↔ Content Store (GitHub API, `dalini/nina-content`); TB-4 Content Store ↔ Site Build (GitHub Actions in `dalini/nina-site`) ↔ Static Hosting (rsync/SSH); TB-5 Instagram ↔ Site Build; TB-6 visitor browser ↔ Google Analytics (the Google tag served by Google, configured by the property settings, and the measurements sent to Google; added in threat model v3).
- Sensitive or regulated data: Editor GitHub credentials and OAuth tokens (the Editing Interface keeps the token in the editor's browser storage, T-45); preview Basic Auth credentials; deploy, preview-deploy and content-read secrets; the build-trigger token, the Instagram token, the GitHub OAuth client secret of the OAuth helper and the SMTP relay credential of the VPS alerts (on the VPS); Nina's email address (published on purpose); image and PDF metadata (EXIF, possibly location); unpublished content, including copies cached in editors' browsers (T-48), the publish status file (T-59) and the backup on the VPS (T-65); visitor IP addresses in nginx access logs (SEC-PRIV-6); visitor and browser data sent to Google Analytics (SEC-PRIV-5); the visitor's consent choice in browser storage (T-72); the Google Analytics property, its settings and its statistics (SEC-PRIV-7).
- External integrations: GitHub (Content Store, OAuth sign-in, Actions); Instagram (Instagram API with Instagram Login, build time); Google Analytics (Google tag with Consent Mode v2 in visitors' browsers on `nina-laaf.de`, SEC-PRIV-5); VPS provider in Germany.
- Authentication model: Editors sign in with individual GitHub accounts through GitHub OAuth, second factor required (SEC-AUTHN-1, SEC-AUTHN-2); preview site: per-editor HTTP Basic Auth over HTTPS. Visitors: none.
- Authorization model: Single role "editor" with full content rights in `dalini/nina-content`; owners add and remove editors; only the maintainer writes `dalini/nina-site`; anyone else has read-only access to published content (FR-10.5).
- Session model: Editing Interface sessions use GitHub OAuth App tokens that do not expire; sign-out deletes the token only in that browser. No inactivity timeout, no session maximum and no clearing of cached content: accepted exception (SEC-AUTHN-3, step 10 again), limited by revocation (SEC-AUTHN-5). Preview site: HTTP Basic Auth.
- Deployment and CI/CD model: GitHub Actions in `dalini/nina-site` (started by the VPS content check through `workflow_dispatch`, plus a nightly schedule) build with Hugo and deploy only the output over rsync/SSH with restricted deploy keys (production and preview); secrets in GitHub Actions secrets of a `production` environment limited to `main` (SEC-SECRET-1, SEC-SECRET-2). Environments and branch protection for private repositories need a paid GitHub plan; `dalini` is a personal account and uses GitHub Pro (T-52; step 10 again, account type checked in step 10 a third time).
- Applicable privacy or regulatory obligations: Operator in Germany: GDPR; Impressum and Datenschutzerklärung required (REQUIREMENTS.md FR-9.1). No GDPR article mapping is kept in this document or the issues.

## Security Rules

### Public site and HTTP boundary (TB-1)

- **SEC-HTTP-1** Static Hosting MUST serve every page and asset of `nina-laaf.de` over HTTPS only, MUST redirect HTTP to HTTPS, and MUST send the header `Strict-Transport-Security: max-age=31536000; includeSubDomains` (no preload).
  - **Applies to:** Static Hosting, all public responses
  - **Verification:** Automated check that HTTP requests redirect and HTTPS responses send HSTS
  - **References:** `REF-ASVS-5`
- **SEC-HTTP-2** Public responses MUST send the Content Security Policy `default-src 'none'; script-src 'self' https://www.googletagmanager.com; style-src 'self'; img-src 'self' https://*.google-analytics.com https://*.googletagmanager.com; connect-src https://*.google-analytics.com https://*.analytics.google.com https://*.googletagmanager.com; font-src 'self'; base-uri 'self'; form-action 'none'; frame-ancestors 'none'`. The only third-party origins are those the Google Analytics 4 tag needs (`REF-GTAG-CSP`, SEC-PRIV-5); the tag's configuration and the Consent Mode defaults come from a first-party script file, never from inline script. If the Google Analytics settings change the origins the tag needs, this policy MUST be updated with them. Instagram media is self-hosted (SEC-PRIV-3). Because `script-src` trusts every script an allowed Google host serves, markup injected into a page could load a Google tag or Tag Manager container that someone else configured (T-76), so `script-src` MUST allow no more Google script than the tag needs: it allows the single host `https://www.googletagmanager.com` (step 10 a third time). It may be widened only if a browser test shows the tag needs more, and the wider source is then recorded in this rule in the same pull request. The build check of SEC-OUT-7 applies whichever source is chosen.
  - **Applies to:** Static Hosting, Public Site
  - **Verification:** Header check in CI; browser test that no third-party request other than to the Google Analytics origins above occurs on page load; review that the recorded `script-src` is the narrowest source with which the SEC-PRIV-5 browser tests pass
  - **References:** `REF-XSS`, `REF-ASVS-5`, `REF-GTAG-CSP`
  - **Threats:** T-34, T-76 (strengthened in v3: narrowest Google script source)
- **SEC-HTTP-3** Public responses MUST send `X-Content-Type-Options: nosniff` and MUST forbid framing of the site by other origins.
  - **Applies to:** Static Hosting
  - **Verification:** Header check in CI
  - **References:** `REF-ASVS-5`
- **SEC-HTTP-4** The Editing Interface (`edit.nina-laaf.de`) and the preview site (`preview.nina-laaf.de`) MUST be served over HTTPS only, MUST redirect HTTP to HTTPS and send an HSTS header, MUST send `X-Content-Type-Options: nosniff`, and MUST forbid framing by other origins. The preview site MUST send the Content Security Policy of SEC-HTTP-2 without the Google origins, and neither host loads Google Analytics. The Editing Interface MUST send a Content Security Policy that allows script only from its own origin (no inline or third-party script), allows connections only to its own origin and the GitHub endpoints the CMS uses, and sets `frame-ancestors 'none'`; the implementer sets the full directive list after testing Sveltia CMS, naming each allowed origin, and records it in this rule in the same pull request (step 10 again).
  - **Applies to:** Editing Interface, preview site (TB-2)
  - **Verification:** The SEC-HTTP-1 and SEC-HTTP-3 header checks, run against both hosts; CSP header check on both hosts; browser test that the Editing Interface loads no script from another origin
  - **References:** `REF-ASVS-5`, `REF-XSS`
  - **Threats:** T-3, T-4, T-45 (strengthened: CSP for the Editing Interface), T-66 (strengthened: CSP for the preview site)
- **SEC-HTTP-5** The TLS certificates of `nina-laaf.de`, `edit.nina-laaf.de` and `preview.nina-laaf.de` MUST be renewed automatically before they expire, and a failed renewal MUST alert Ives. Certificates come from Let's Encrypt with automatic renewal (certbot or lego); a failed renewal MUST be emailed to Ives from the VPS through an SMTP relay. The same email alert path serves the Instagram token refresh (SEC-SECRET-3) and the content check (SEC-CICD-4). Mail leaves the VPS only through a local mail relay agent (e.g. nullmailer or msmtp with a queue) that runs under its own unprivileged account and is the only account that reads the relay credential (SEC-SECRET-1); the alerting jobs hand their messages to the local `sendmail` interface and never read the credential (step 10 a third time, PQ-56).
  - **Applies to:** Static Hosting (TB-1, TB-2)
  - **Verification:** Automated check of each host's certificate expiry date; review of the renewal job; a test alert reaches Ives by email
  - **References:** `REF-ASVS-5`
  - **Threats:** T-64

### Domain, DNS and hosting accounts (TB-1)

- **SEC-HOST-1** The registrar, DNS and VPS accounts for `nina-laaf.de` MUST be held by named people (today and in future: Ives) with individual logins and a second factor wherever the provider offers one; renewal notices MUST go to a monitored address; a DNS record MUST be removed when the target it points to is retired.
  - **Applies to:** Domain and DNS of `nina-laaf.de`, Static Hosting
  - **Verification:** Yearly manual review by Ives of account holders, second factors, renewal date and DNS records against live targets
  - **References:** `REF-ASVS-5`, `REF-SSDF`
  - **Threats:** T-26, T-27
- **SEC-HOST-2** The VPS MUST receive operating-system and package security updates daily and unattended (e.g. unattended-upgrades), with an automatic reboot at night when an update requires one, MUST allow administrative access only over SSH with keys (no password sign-in, no direct root sign-in), and MUST expose only HTTP, HTTPS and SSH to the internet. Every process that handles input from outside the VPS (nginx workers, the OAuth helper, the content check, the Instagram token refresh, the backup, the deploy account's rsync, the mail relay agent) MUST run under an unprivileged account, never as root, and reads only its own secrets (SEC-SECRET-1).
  - **Applies to:** Static Hosting (VPS)
  - **Verification:** External port scan shows only 22, 80 and 443; SSH password and root sign-in are rejected; the process list shows none of the listed processes running as root; the unattended-upgrade log is checked in the yearly SEC-HOST-1 review
  - **References:** `REF-ASVS-5`, `REF-SSDF`
  - **Threats:** T-61, T-62

### Third-party content and privacy

- **SEC-PRIV-1** The Public Site MUST NOT request any third-party resource (fonts, scripts, images, embeds such as Instagram/Meta, video or maps) in the visitor's browser, with one exception: Google Analytics under SEC-PRIV-5 (step 10 again). Fonts and all site assets MUST be self-hosted.
  - **Applies to:** Public Site, Site Build templates
  - **Verification:** Automated browser test recording all network requests on every page type, before and after consent: only the site's own origin and the Google Analytics origins of SEC-HTTP-2 are contacted
  - **References:** `REF-PC-2024`
- **SEC-PRIV-2** WITHDRAWN in step 10: it applied only to a browser-loaded Instagram feed (model (a)); the build-time model (b) was chosen, so visitors never contact Instagram (SEC-PRIV-3).
- **SEC-PRIV-3** The Site Build MUST copy Instagram post images into the static output so that visitors never request them from Instagram.
  - **Applies to:** Instagram Feed Integration, Site Build
  - **Verification:** Build output contains no Instagram/Meta URLs for media; browser test as SEC-PRIV-1
  - **References:** `REF-PC-2024`
- **SEC-PRIV-4** The Site Build or upload process MUST remove EXIF and other embedded metadata (including location) from published images, and MUST remove embedded metadata (author, software, location in embedded images) from published PDFs automatically, so that a publish never fails for PDF metadata (step 10 again), except the copyright notice and the creator (photographer or author), which are kept.
  - **Applies to:** Editing Interface uploads, Site Build image processing
  - **Verification:** Automated check that no image or PDF file anywhere in the build output contains GPS or device metadata
  - **References:** `REF-PC-2024`
  - **Threats:** T-25 (strengthened: PDFs, whole build output)
- **SEC-PRIV-5** Visitor statistics MUST use Google Analytics (GA4) on the public site `nina-laaf.de` only; `edit.nina-laaf.de` and `preview.nina-laaf.de` MUST NOT load it, and neither the preview build nor the Editing Interface files may contain the Google tag loader or the measurement ID (T-85). The Google tag MUST run with Google Consent Mode v2 in its advanced form: a first-party script sets analytics and ad consent to denied before the tag loads; until the visitor accepts in the consent banner (REQUIREMENTS.md FR-9.2), the tag sends only cookieless pings and sets no cookies; Accept grants analytics consent; Decline or withdrawal sets it back to denied. In addition (threat model v3): only the first-party consent script inserts the Google tag, after it has set the defaults, and no page contains the tag itself, so the tag does not load when that script does not run (T-71); the site loads only the Google tag of the property's own GA4 measurement ID, with no Google Tag Manager container and no other destination (T-69, T-70); `ad_storage`, `ad_user_data` and `ad_personalization` stay denied in every state, and Accept grants `analytics_storage` only; only a stored value that exactly matches Accept counts as consent, and a missing, unknown or malformed value counts as no choice: the banner is shown and consent stays denied (T-72); Google Analytics cookies are set for the host `nina-laaf.de` only (the tag's cookie domain set to that host instead of Google's automatic highest-level domain), so they are not sent to `edit.nina-laaf.de` or `preview.nina-laaf.de` (`REF-GTAG-COOKIES`, T-79). Which `cookie_domain` value gives host-only cookies (no `Domain` attribute; e.g. the host name or `'none'`) is verified at implementation in a browser test and recorded here; if no value does, cookies for `nina-laaf.de` are an accepted risk: `edit.` and `preview.` neither read nor log them (step 10 a third time, PQ-61). The preview build contains neither the consent script nor its footer link (REQUIREMENTS.md FR-9.2; PQ-62). The stored consent choice records the banner version it answered; a choice for another version counts as no choice (T-72, T-73; SEC-PRIV-7). The property is owned by Ives, Nina has read access, Google's data processing terms are accepted, and the property keeps Google's default data settings; its administration: SEC-PRIV-7. Google Analytics, Consent Mode and the consent choice stored in the browser MUST be described in the Datenschutzerklärung. No other analytics or tracking script, cookie or pixel is allowed. Accepted risk (step 10 again; modeled in threat model v3, T-69, T-74, T-75): Google receives visitors' IP addresses and browser data, also before consent through the cookieless pings; the Google script runs in the site's origin with access to every page and is served live by Google, so it cannot be pinned or checked as SEC-CICD-2 requires for other third-party code; anyone who knows the public measurement ID can send false measurements to the property.
  - **Applies to:** Public Site, Site Build templates
  - **Verification:** Browser test: before consent no Google cookie is set and only cookieless requests reach the Google origins; after Accept analytics cookies are set, for the host `nina-laaf.de` only, and the consent state sent to Google grants no ad consent type; after Decline or withdrawal they are not set again; with the consent script blocked, no request reaches a Google origin; with an unknown stored value, the banner is shown and no Google cookie is set; no Google request from `edit.nina-laaf.de` or `preview.nina-laaf.de`; build test: the preview output and the Editing Interface files contain no measurement ID and no tag loader; no other analytics script in the build output; Datenschutzerklärung text reviewed
  - **References:** `REF-PC-2024`, `REF-GTAG-CSP`, `REF-GTAG-CONSENT`, `REF-GTAG-COOKIES`
  - **Threats:** T-34 (changed: Google Analytics is the allowed exception), T-63 (no longer applies: no statistics from the logs), T-69, T-74, T-75 (accepted), T-71, T-72, T-79, T-85 (strengthened in v3)
- **SEC-PRIV-6** nginx access logs MAY contain full visitor IP addresses for abuse handling only (not for statistics); they MUST be deleted after 14 days, MUST be readable only by the maintainer, and MUST be described in the Datenschutzerklärung.
  - **Applies to:** Static Hosting
  - **Verification:** Review of nginx log configuration and log rotation (14 days); file permissions; Datenschutzerklärung text
  - **References:** `REF-PC-2024`
  - **Threats:** T-30
- **SEC-PRIV-7** The Google Analytics property (SEC-PRIV-5) MUST be administered as follows. The Google account that owns it (Ives's) MUST have a second factor. Ives is the only Administrator, Nina has the Viewer role, and nobody else has access. The data collection settings of the property and its web data stream (among them enhanced measurement, data redaction, Google signals and user-provided data collection), links to other Google products and additional destinations of the Google tag change what the tag collects in visitors' browsers without a change in `dalini/nina-site` (`REF-GA4-EM`); they MUST NOT be changed from Google's defaults unless this rule, SEC-PRIV-5, SEC-HTTP-2 and the Datenschutzerklärung are updated first. Email redaction, on by default for new properties (`REF-GA4-REDACT`), MUST stay on. No Google Tag Manager container and no linked Tag Manager or Google Ads product may be used with the property; the site loads `gtag.js` for the property's measurement ID only, and Ives checks this in the property review (step 10 a third time; replaces the v3 assumption that property settings cannot add script). The consent banner has a version (REQUIREMENTS.md FR-9.2): Ives MUST raise it in the same change whenever the banner text, the purposes or any setting named in this rule changes, so that every visitor is asked again (T-73). Consent is not recorded outside the visitor's browser (step 10 a third time, SQ-23).
  - **Applies to:** Google Analytics property (TB-6)
  - **Verification:** Yearly review by Ives, as part of the SEC-HOST-1 review: second factor on the owning account; the property's user list; the property and data stream settings against Google's defaults and against the property change history
  - **References:** `REF-GA4-EM`, `REF-GA4-REDACT`, `REF-ASVS-5`
  - **Threats:** T-70 (added in v3)

### Output encoding and safe rendering

- **SEC-OUT-1** The Site Build MUST HTML-encode all editor-provided text by default. Rich text is allowed only in Text bodies, Page content, News text, a work's short text and the CV bio, and MUST be rendered from a restricted format: paragraphs, headings h2–h3, bold, italic, links, lists, block quotes, and (in Text bodies only) images from the Content Store; every other field is plain text. Raw HTML, scripts, inline event handlers, iframes and `javascript:` URLs in content MUST be removed or rejected.
  - **Applies to:** Site Build templates, content model
  - **Verification:** Build tests with content containing `<script>`, event-handler attributes and `javascript:` links; output must contain none of them
  - **References:** `REF-XSS`
- **SEC-OUT-2** External links from content (exhibition links, gallery, Instagram) MUST use only `https:` or `mailto:` schemes and MUST open without giving the target page access to the site (`rel="noopener"`).
  - **Applies to:** Content model, Site Build
  - **Verification:** Build test rejecting other schemes
  - **References:** `REF-XSS`, `REF-INPUT`
- **SEC-OUT-3** Content imported from Instagram (captions, links) MUST be treated as untrusted text and encoded like editor content. The Site Build MUST fetch it over HTTPS with certificate validation, and fetched media MUST pass the type checks of SEC-INPUT-1 and the limits of SEC-INPUT-5. A fetched post that fails one of these checks MUST be left out like a hidden post (REQUIREMENTS.md FR-8.5) and MUST NOT fail the build.
  - **Applies to:** Instagram Feed Integration, Site Build
  - **Verification:** Build test with a caption containing markup; build test with a fetched file that is not an image or exceeds the SEC-INPUT-5 limit: the build publishes, the post is left out, nothing of it is in the output
  - **References:** `REF-XSS`
  - **Threats:** T-38 (strengthened: transport and media checks), T-68 (strengthened: a failing post does not fail the build)
- **SEC-OUT-4** The Editing Interface MUST display content (lists, forms, previews) with the same encoding and restricted rich-text rules as SEC-OUT-1. It MUST show the publish status file (DF-9) as text only.
  - **Applies to:** Editing Interface
  - **Verification:** Open content containing `<script>`, event-handler attributes and `javascript:` links in every Editing Interface view: no script runs; a status file containing markup is shown as text
  - **References:** `REF-XSS`
  - **Threats:** T-5, T-60 (strengthened: publish status file)
- **SEC-OUT-5** The Public Site's first-party client-side code (e.g. the image viewer) MUST insert values from the URL, browser storage or page data into the page only as text, never as HTML.
  - **Applies to:** Public Site client-side code
  - **Verification:** Browser test with markup in the query string, fragment and stored values: rendered as text, no script runs
  - **References:** `REF-XSS`
  - **Threats:** T-32
- **SEC-OUT-6** WITHDRAWN in step 10: it applied only to a browser-loaded Instagram feed (model (a)); with the build-time model no Instagram/Meta script reaches visitors (SEC-HTTP-2 allows only `'self'`).
- **SEC-OUT-7** The Site Build MUST fail and publish nothing (as in SEC-INPUT-3) when a generated page contains a script element other than one that loads one of the site's own script files, an inline script, an inline event-handler attribute or a `javascript:` URL. The Google tag is inserted at runtime by the first-party consent script (SEC-PRIV-5) and never appears in a generated page. The check runs on the output of the production and the preview build, whatever put the markup there (template, content, Instagram caption).
  - **Applies to:** Site Build (TB-4)
  - **Verification:** Build tests with a generated page containing an external `<script>` element naming a Google host, an inline script, and an event-handler attribute: each build fails and the live site is unchanged
  - **References:** `REF-XSS`
  - **Threats:** T-76, T-77 (added in v3)

### Editing access (TB-2, TB-3)

- **SEC-AUTHN-1** The Editing Interface MUST require authentication for every action that reads unpublished content or changes content. Mechanism: GitHub OAuth sign-in through the OAuth helper self-hosted on `edit.nina-laaf.de`; the preview site requires per-editor HTTP Basic Auth over HTTPS.
  - **Applies to:** Editing Interface, preview site
  - **Verification:** Automated test: unauthenticated requests to every editing action and to the preview site are rejected
  - **References:** `REF-AUTH`, `REF-SESSION`
- **SEC-AUTHN-2** Every editor MUST sign in with an individual account (no shared accounts), and the sign-in (the editing system's own or an identity provider's) MUST resist credential guessing by limiting or slowing repeated failed attempts (GitHub's sign-in for the CMS; nginx limits for the preview site). Every editor's GitHub account MUST have a second factor enabled. Preview passwords MUST be unique per editor, MUST NOT be the editor's GitHub password, and MUST be stored only as salted hashes made with the strongest `crypt()` method the VPS supports (no plain, SHA-1 or MD5-based entries).
  - **Applies to:** Editing Interface, preview site (TB-2)
  - **Verification:** Review: one GitHub account and one preview credential per listed editor, each with 2FA on GitHub; automated test: repeated failed preview sign-ins are limited; review of the hash method of every entry in the preview password file
  - **References:** `REF-AUTH`
  - **Threats:** T-1, T-67 (strengthened: preview password storage)
- **SEC-AUTHN-3** Each sign-in to the Editing Interface MUST obtain a new token; tokens and session values MUST NOT appear in URLs or logs; state-changing editing actions MUST be protected against cross-site request forgery. Accepted exception (step 10 again, SQ-16): the Editing Interface uses GitHub OAuth App tokens that do not expire, and sign-out deletes the token only in that browser. There is no inactivity timeout and no session maximum, and sign-out does not remove the content the Editing Interface cached on the device. Editors sign in only on their own devices; the risk is limited by revocation (SEC-AUTHN-5).
  - **Applies to:** Editing Interface (TB-2)
  - **Verification:** Automated tests: a forged cross-site request is rejected; URLs and logs contain no token or session values; revocation drill (SEC-AUTHN-5)
  - **References:** `REF-SESSION`
  - **Threats:** T-2, T-3, T-47, T-48 (accepted in step 10 again)
- **SEC-AUTHN-4** The OAuth helper on `edit.nina-laaf.de` MUST release a token only to pages served from `https://edit.nina-laaf.de` (its allowed-domains setting set to exactly that host), MUST verify the OAuth `state` value of every sign-in, MUST request only the scopes SEC-AUTHZ-3 allows, and MUST never request the `workflow` scope. Its GitHub OAuth client secret is a secret under SEC-SECRET-1. The helper is a Deno port of the Sveltia CMS Authenticator (`REF-SVELTIA-AUTH`), kept in `dalini/nina-site` and maintained by Ives; it runs on the VPS under its own unprivileged account (SEC-HOST-2) with a pinned Deno version and pinned dependencies (SEC-CICD-2, DEP-1 to DEP-8), installed by hand by Ives from a tagged release (SEC-CICD-2). The port MUST compare the full origin (scheme and host) of the page that receives the token, and an empty allowed-domains setting MUST release no token (upstream, it then releases the token to any page and compares host names only; T-80). Because `nina-laaf.de`, `edit.nina-laaf.de` and `preview.nina-laaf.de` are one site for cookies, script in the public origin can set cookies that the browser sends to the helper (T-78): every cookie the helper sets MUST use the `__Host-` prefix (`Secure`, `Path=/`, no `Domain`; `REF-COOKIE-PREFIX`), and a callback whose request carries more than one state cookie MUST be rejected. Deno MUST run the helper with only the permissions it needs (`REF-DENO-PERM`): network access to its listening address and GitHub's OAuth endpoint, read access to its own code and its own secret file, and its own environment variables; never `--allow-all`, and no permission to write files, run programs or load native libraries (T-80).
  - **Applies to:** Editing Interface OAuth helper (TB-2, TB-3)
  - **Verification:** A sign-in started from another origin, or from `http://edit.nina-laaf.de`, receives no token; with an empty allowed-domains setting no token is released; a callback with a wrong or missing `state` is rejected; a callback that also carries a state cookie set for `.nina-laaf.de` is rejected; the helper's cookies carry the `__Host-` prefix; the helper's start command is reviewed for its Deno permission flags; the scopes shown on GitHub's authorization screen are reviewed
  - **References:** `REF-AUTH`, `REF-SVELTIA-AUTH`, `REF-COOKIE-PREFIX`, `REF-DENO-PERM`
  - **Threats:** T-43, T-78, T-80 (strengthened in v3: `__Host-` cookies, full origin, Deno permissions)
- **SEC-AUTHN-5** Ives MUST be able to revoke all Editing Interface tokens of an editor at once (by revoking that editor's authorization of the OAuth app, or all tokens of the app), and MUST do so when an editor reports a lost device, when an editor is removed (SEC-AUTHZ-2), and after a suspected compromise.
  - **Applies to:** Editing Interface, Content Store (TB-3)
  - **Verification:** Revocation drill: after revocation, the Editing Interface on the old device can no longer read or write the Content Store
  - **References:** `REF-SESSION`, `REF-AUTH`
  - **Threats:** T-44, T-47
- **SEC-AUTHZ-1** The Content Store MUST accept changes only from authenticated editors on its allow-list (the GitHub collaborators of `dalini/nina-content`: Nina and Ives) and MUST deny everything else by default, leaving the site unchanged.
  - **Applies to:** Content Store, Editing Interface
  - **Verification:** Test with a non-listed account: change is rejected and the site is unchanged
  - **References:** `REF-ASVS-5`, `REF-PC-2024`
- **SEC-AUTHZ-2** Adding or removing editors MUST be decided only by the owners (Nina and Ives) and carried out only by Ives, the sole GitHub admin of `dalini/nina-content`. Every change MUST also be committed as a line in `EDITORS.md` in the Content Store.
  - **Applies to:** Content Store
  - **Verification:** Manual review: collaborator list matches `EDITORS.md`; Ives is the only admin; history shows each change
  - **References:** `REF-ASVS-5`
- **SEC-AUTHZ-3** Editors' write access, and the credential the Editing Interface uses to write to the Content Store, MUST be limited to content and media (plus adding and removing editors under SEC-AUTHZ-2). They MUST NOT be able to change templates, build configuration or pipeline definitions: those live in `dalini/nina-site`, where only the maintainer has write access (ARCHITECTURE.md DR-8). Accepted risk: Ives is both editor and maintainer, so his CMS OAuth token can also write `dalini/nina-site`; this is accepted for his account, which requires 2FA.
  - **Accepted risk (step 10 again, SQ-17, T-44):** the Editing Interface keeps the GitHub OAuth App with the authenticator's default scope `repo,user`, which reaches every repository the signed-in editor can access and, for Ives, also his admin rights on `dalini/nina-content` and his other repositories. This wider reach is accepted explicitly; it is limited by the second factor (SEC-AUTHN-2) and revocation (SEC-AUTHN-5).
  - **Applies to:** Content Store, Editing Interface, Site Build (TB-3, TB-4)
  - **Verification:** Test with Nina's editor account and the Editing Interface credential: a push to `dalini/nina-site` is rejected; review that only Ives has write access there; review of the scopes or permissions granted to the Editing Interface credential
  - **References:** `REF-CICD`, `REF-ASVS-5`, `REF-SVELTIA-AUTH`
  - **Threats:** T-11, T-44
- **SEC-AUTHZ-4** The Content Store, including its history and media originals, MUST NOT be publicly readable; read access is limited to editors, the build identity and the VPS content check and backup (read-only credentials), and the maintainer (Ives).
  - **Applies to:** Content Store (TB-3)
  - **Verification:** Unauthenticated read request is rejected; review of the access list
  - **References:** `REF-ASVS-5`
  - **Threats:** T-13

### Change history and recovery

- **SEC-AUDIT-1** Every change in the Content Store MUST record which authenticated editor made it, taken from the Editing Interface sign-in rather than from self-declared author fields, and when. Editors, the Editing Interface and the build identity MUST NOT be able to rewrite or delete history (branch protection on `main` of `dalini/nina-content`). Exception: on a documented legal request (withdrawn image rights, personal data entered by mistake), only Ives may purge the content from history and backups, and MUST keep a record of the purge (date and the kind of reason, e.g. withdrawn image rights; no content). Because the record may be kept in the public `docs/ops/` (T-83), it MUST NOT name the purged item, file or person. `main` of `dalini/nina-content` MUST accept only commits that GitHub marks as verified, so that the author of a direct push cannot be self-declared. This is checked at implementation: if the commits the Editing Interface makes through GitHub's API are not marked verified, this verified-commits requirement is dropped and self-declared authors on direct pushes are accepted (T-53; step 10 again). Branch protection and required verified commits on a private repository need a paid GitHub plan, which `dalini` uses (GitHub Pro, as a personal account; step 10 again).
  - **Applies to:** Content Store, Editing Interface
  - **Verification:** Changes by two editors show each identity in the history; an attempt to rewrite history with editor, Editing Interface or build credentials is rejected; a direct push of an unsigned commit naming another editor is rejected; purge records name no purged item, file or person
  - **References:** `REF-ASVS-5`, `REF-GH-PLANS`
  - **Threats:** T-9, T-15, T-52, T-53 (strengthened: verified commits), T-83 (strengthened in v3: purge record)
- **SEC-AUDIT-2** Every production deploy MUST record the Content Store version it was built from and what triggered it, and the previously deployed version MUST be restorable without a new content change.
  - **Applies to:** Site Build, Static Hosting (TB-4)
  - **Verification:** Review of deploy records; restore drill to the previous version
  - **References:** `REF-SSDF`
  - **Threats:** T-23, T-27
- **SEC-AVAIL-1** Content and media originals MUST be backed up to a location that does not depend on the Content Store's account or provider, and restoring from the backup MUST be tested. A mirror of `dalini/nina-content` (history and originals) MUST be made weekly to the VPS and kept for 30 days; Ives tests a restore once a year. The backup MUST be stored outside every directory nginx serves and MUST be readable only by the maintainer, not by the web server, deploy or OAuth-helper accounts. Residual risk: the backup is independent of GitHub, but not of the VPS that also runs Static Hosting.
  - **Applies to:** Content Store, Static Hosting (VPS)
  - **Verification:** Yearly restore test into an empty store; the Site Build produces the same site from it; file permissions and nginx roots reviewed against the backup path
  - **References:** `REF-SSDF`
  - **Threats:** T-16, T-65 (strengthened: location and access on the VPS)

### Uploads and content validation

- **SEC-INPUT-1** The Editing Interface MUST accept only image files and PDFs for upload, check the actual file type (not only the extension), and reject images above 10 MB and PDFs above 20 MB. Because these checks run in the editor's browser and a direct write to the Content Store bypasses them, the Site Build MUST recheck the type and size of every file it publishes; a failed check fails the publish under SEC-INPUT-3. Where the Editing Interface cannot check the actual file type at upload, the Site Build check is the enforcement point (REQUIREMENTS.md FR-10.6).
  - **Applies to:** Editing Interface, Content Store, Site Build
  - **Verification:** Upload tests with a renamed executable, an SVG with script, and an oversized file; the same files committed directly to the Content Store: the publish fails
  - **References:** `REF-INPUT`
  - **Threats:** T-7, T-49 (strengthened: recheck in the Site Build)
- **SEC-INPUT-2** SVG uploads MUST be rejected unless sanitized; this applies to editor uploads, not to the site's own `logo.svg`. The Site Build MUST apply the same rule to every SVG from the Content Store it would publish.
  - **Applies to:** Editing Interface, Site Build
  - **Verification:** Upload test with an SVG containing script; the same SVG committed directly to the Content Store: the publish fails
  - **References:** `REF-INPUT`, `REF-XSS`
  - **Threats:** T-7, T-49 (strengthened: recheck in the Site Build)
- **SEC-INPUT-3** The Site Build MUST fail and publish nothing when content violates the content model (FR-10.6, ARCHITECTURE.md DR-3), leaving the previous site online.
  - **Applies to:** Site Build, Static Hosting
  - **Verification:** Build with an invalid work entry: build fails; live site unchanged
  - **References:** `REF-INPUT`
- **SEC-INPUT-4** Unpublished content MUST NOT appear in the production output (FR-11.2); only the preview build includes it (SEC-CICD-3).
  - **Applies to:** Site Build
  - **Verification:** Production build test with an unpublished work: no page, no image, no listing entry
  - **References:** `REF-ASVS-5`
- **SEC-INPUT-5** Image processing (at upload and in the Site Build, including Instagram media) MUST reject images larger than 40 megapixels before decoding them fully. Where the Editing Interface cannot check pixel dimensions at upload, the Site Build check is the enforcement point (REQUIREMENTS.md FR-10.6).
  - **Applies to:** Editing Interface uploads, Site Build image processing
  - **Verification:** Upload and build tests with a small file declaring extreme pixel dimensions: upload rejected; build fails under SEC-INPUT-3 without exhausting memory or time
  - **References:** `REF-INPUT`
  - **Threats:** T-8, T-38
- **SEC-INPUT-6** The Site Build MUST treat content fields as data: template, shortcode or other generator syntax inside content MUST NOT be evaluated. Content MUST NOT control how the generator renders it (T-77): the Site Build MUST fail the publish (SEC-INPUT-3) when a content file is not Markdown, or when its front matter holds a field that the content model in `dalini/nina-site` does not document (ARCHITECTURE.md DR-3, DR-4). The content model MUST NOT use fields the generator interprets itself to choose a page's URL, template, output or renderer (in Hugo among others `url`, `aliases`, `layout`, `type`, `outputs`, `cascade`, `build`, `markup`; `REF-HUGO-SEC`), except `slug` under the rule below. Hugo's `security.allowContent` setting MUST keep its default, which denies HTML content files (CVE-2026-50133, fixed in v0.162.0). A URL segment taken from content (e.g. the slug of an Exhibition entry, REQUIREMENTS.md FR-4.7) MUST consist only of lowercase letters, digits and hyphens. An Exhibition slug is generated once from the title and start year (umlauts and ß transliterated, other characters replaced by hyphens); the Site Build MUST fail the publish when two entries share a slug, naming both (FR-4.7).
  - **Applies to:** Site Build (TB-4), content model
  - **Verification:** Build test with generator template and shortcode syntax in a text field: the output shows it as encoded text; build tests with a content file in HTML format, with `markup: html`, with `url` or `aliases` naming the Impressum, and with a slug containing `/` or `..`: each publish fails and the live site is unchanged
  - **References:** `REF-INPUT`, `REF-HUGO-SEC`
  - **Threats:** T-18, T-77 (strengthened in v3: generator-reserved fields and content formats)
- **SEC-INPUT-7** The Site Build MUST fail and publish nothing when the Content Store checkout contains a symbolic link or any other entry that is not a regular file or directory.
  - **Applies to:** Site Build (TB-4)
  - **Verification:** Build test with a symbolic link in the content pointing outside the checkout: the build fails and the output contains nothing from the link target
  - **References:** `REF-INPUT`, `REF-HUGO-ADV`
  - **Threats:** T-50

### Secrets and pipeline (TB-4)

The Instagram token belongs to the deploy account, which also runs its monthly refresh (SEC-SECRET-3). Ives rotates them at least yearly and after any suspected leak. No secret or credential may be kept in the public specification repository `dalini/nina-website` either, including its operational records in `docs/ops/` (ARCHITECTURE.md Repositories), which MUST also hold no personal data beyond the editors' names (T-83).
  - **Applies to:** Site Build, Static Hosting, Instagram Feed Integration, Editing Interface OAuth helper, `docs/ops/` of `dalini/nina-website`

- **SEC-CICD-1** The build/deploy identity MUST have only the permissions needed to publish the site: read-only access to `dalini/nina-content`, and an SSH deploy key restricted to writing the web root (plus reading the Instagram token and the deployed feed files, ARCHITECTURE.md).   - **References:** `REF-CICD`, `REF-SSDF`

  - **Applies to:** Site Build pipeline, Editing Interface

## Dependency Security Rules

These are prospective rules; no dependency has been assessed yet. References: `REF-SUPPLY`, `REF-DEPS`, `REF-SSDF`.

- **DEP-1** The project MUST NOT add a dependency when the standard library or a small amount of straightforward, non-security-sensitive first-party code is safer and sufficient. The project MUST NOT replace vetted cryptography, authentication, authorization, protocol parsing, output encoding, HTML sanitization, or other security-critical functionality with custom code merely to avoid a dependency.
- **DEP-2** The project SHOULD prefer zero new dependencies. Every new dependency MUST be justified in the pull request description, including its purpose and why existing code or platform functionality is insufficient.
- **DEP-3** A new dependency MUST show evidence of active maintenance through a stable release, security response, or substantive maintainer activity within the previous 12 months. A mature project with less frequent releases requires an explicit documented exception and evidence that security reports are still handled.
- **DEP-4** The project MUST use the latest stable release from the latest actively supported major version unless a documented compatibility constraint requires another actively supported major version. Deprecated, abandoned, end-of-life, or pre-release packages MUST NOT be introduced into production.
- **DEP-5** Before a dependency is added or updated, direct and transitive dependencies MUST be checked for known vulnerabilities. A dependency with a known unpatched vulnerability applicable to the intended use MUST NOT be introduced without explicit, time-bounded risk acceptance, documented compensating controls, and a remediation plan.
- **DEP-6** Dependency review MUST include the complete transitive dependency graph. A small direct dependency with a disproportionately large, opaque, abandoned, or unvetted transitive tree SHOULD be rejected.
- **DEP-7** Production builds MUST resolve dependencies to exact versions through a committed lockfile or equivalent ecosystem mechanism. Production and CI builds MUST use frozen or reproducible dependency resolution and MUST NOT resolve floating versions at build or deployment time.
- **DEP-8** When multiple suitable libraries exist, the project SHOULD prefer the library with the narrowest required scope, smallest dependency tree, active security response process, clear provenance, and established security track record.

Why no credible threat was identified:

- **OAuth helper, Repudiation:** the helper only relays the GitHub sign-in; GitHub records each authorization in the editor's own account, and changes are attributed in the Content Store (SEC-AUDIT-1).
- **Content Store, Spoofing:** the store has no sign-in of its own in the documents; impersonating an editor is T-1, writing as a non-listed party is T-12.
- **Publish trigger, Elevation of Privilege:** the trigger token can only start the build workflow of `dalini/nina-site`; it cannot change content or code (T-22); command injection through the call is T-55.
- **Publish status file, Spoofing / Repudiation / EoP:** only the Site Build writes it, over the deploy channel (writing it as someone else is T-60); it records no user action; it grants no rights (DR-1).
- **Preview site, Repudiation / EoP:** visitors of the preview only read static files; no server-side code serves them.
- **Static Hosting, Repudiation:** visitors perform no actions; Ives is the only operator, and unattributed changes to served files are covered by T-23 and T-27.
- **VPS jobs, Spoofing / Repudiation:** the jobs only connect out (to GitHub and Instagram, over verified HTTPS) and take no requests; their runs are visible in the build records (SEC-AUDIT-2) and their alerts (SEC-CICD-4, SEC-SECRET-3).
- **Public Site, Spoofing:** visitors have no identity; impersonating the site itself is T-26.
- **Public Site, Repudiation:** visitors are anonymous and change nothing.
- **Public Site, Denial of Service:** pages are static and do no processing a visitor can exhaust; flooding the host is T-31.
- **Instagram, Repudiation:** the integration is read-only and performs no user actions.
- **Instagram, Information Disclosure:** with the build-time model visitors never contact Instagram (T-40 no longer applies); the token is T-37.
- **Legacy import, Spoofing / Repudiation / DoS / EoP:** a one-time import of known files; the result passes the same build checks (SEC-INPUT-3, SEC-INPUT-6, SEC-INPUT-7) and change history (SEC-AUDIT-1) as editor content.
- **Contact by email, all but Information Disclosure:** the site publishes only a `mailto:` link; the mail system is outside this system; tampering with the page is T-27; spam volume is part of T-42.
- **Consent banner, Spoofing / EoP:** visitors have no identity, and the banner acts only in the visitor's own browser; it holds no rights beyond the page, and script injected through it is T-32 (SEC-OUT-5).
- **Google tag, Repudiation:** measurements are not actions anyone must answer for; changes to the settings that drive them are recorded in the property change history (SEC-PRIV-7).
- **Google Analytics property, Repudiation:** the property change history records who changed which setting and when (SEC-PRIV-7 verification).
- **Google Analytics property, Denial of Service:** losing the property or its data loses statistics only; the site works without them (an unavailable tag is T-84).
- **Google Analytics property, EoP:** a role on the property gives no access to the site, the Content Store or the VPS. Google Tag Manager containers can add script of their own choosing; whether GA4 property settings can was not confirmed, so SEC-PRIV-7 forbids Tag Manager containers and linked Tag Manager or Ads products, and the site loads `gtag.js` for the measurement ID only (step 10 a third time; was an ASSUMPTION in v3).
- **`docs/ops/`, all but Information Disclosure:** the records are plain text in the repository's Git history, which attributes every change; they hold no secrets (SEC-SECRET-1), so they grant nothing.

Version 1 found no credible Elevation of Privilege on Static Hosting because no server-side code serves visitors. Version 2 changes that cell: the VPS now also runs the OAuth helper and jobs that parse outside data (T-61).
